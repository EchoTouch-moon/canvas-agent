# Canvas Agent UI 设计与开发基线

**版本：UI Baseline v1.0**  
**纳入项目基线：Design Baseline v1.1**  
**确认日期：2026 年 8 月 6 日**  
**状态：CONFIRMED**

---

# 一、决策摘要

Canvas Agent 正式采用以下 UI 开发基调：

```text
基础设计体系：shadcn/ui
组件底层：Base UI
默认视觉风格：Rhea
样式体系：Tailwind CSS + CSS Variables
图标：Lucide
复杂表格：TanStack Table
局部关系图：React Flow / React Flow UI
业务组件：Canvas Agent 自建领域组件
```

其中：

- **shadcn/ui** 提供组件源码、默认审美、组合方式和可访问性基础；
- **Base UI** 提供无样式、可组合的交互原语；
- **Rhea** 作为默认视觉风格，提供较紧凑但不过度生硬的信息密度；
- **Mira** 仅作为高密度对照原型，不作为默认基线；
- **TanStack Table** 提供表格状态和数据处理能力，视觉继续遵循 Canvas Agent Token；
- **React Flow** 只承担局部关系图、上下文来源图和影响分析，不成为产品主界面。

该决定不是“直接套用一个 shadcn Dashboard 模板”，而是：

> **使用成熟的组件与视觉基础，围绕 Canvas Agent 自身的信息架构、领域对象和核心工作流建立独立产品体验。**

---

# 二、选择目标

本方案主要解决以下问题：

1. 避免由开发者或 Agent 在不同页面中凭感觉重复设计；
2. 建立统一的颜色、间距、字体、状态和交互基线；
3. 让 Codex 等编程 Agent 能直接读取并复用项目中的组件源码；
4. 支持 Context Composer、Run Timeline、Artifact Review 等高度定制界面；
5. 保持桌面生产力工具所需的信息密度；
6. 避免产品最终变成传统企业后台或模板拼接应用；
7. 允许未来逐步形成 Canvas Agent 自己的组件 Registry。

---

# 三、产品视觉定位

Canvas Agent 的视觉定位为：

> **克制、紧凑、结构清晰的桌面生产力工作台。**

主要参考气质：

- IDE 与代码工作区；
- Git 客户端；
- Linear 类任务工具；
- 数据与知识工作台；
- 本地优先桌面应用。

不采用以下方向：

- 大量渐变和装饰性动效；
- 巨型圆角卡片；
- 营销网站式大留白；
- 每个区域都使用独立卡片包裹；
- 依赖阴影区分所有层级；
- 传统后台的“查询表单 + 表格 + 抽屉”单一范式；
- 为了展示 Canvas 而把所有内容节点化。

基础视觉原则：

```text
中性背景
少量强调色
边框多于阴影
适度圆角
紧凑但不拥挤
高信息密度
明确的选中与焦点状态
稳定的语义状态色
深色与浅色主题并行
键盘操作优先
```

# 四、UI 架构分层

UI 代码按五层组织：

```text
设计 Token
    ↓
通用 UI 原语
    ↓
应用级组合组件
    ↓
Canvas Agent 领域组件
    ↓
页面与用户流程
```

## 4.1 设计 Token

Token 统一定义：

- 背景、前景、边框和浮层颜色；
- 主强调色；
- 成功、警告、失败、等待、信息状态；
- 字体家族、字号与行高；
- 间距和控件高度；
- 圆角；
- 阴影；
- 动画时长；
- 面板宽度；
- Z-Index 层级。

业务代码不得直接大量使用硬编码色值。

优先使用语义 Token：

```text
--background
--foreground
--muted
--border
--primary
--destructive
--status-success
--status-warning
--status-waiting
--status-running
--status-stale
--status-diverged
```

## 4.2 通用 UI 原语

目录：

```text
components/ui/
```

主要来自 shadcn/ui，例如：

- Button；
- Input；
- Textarea；
- Dialog；
- AlertDialog；
- Popover；
- DropdownMenu；
- ContextMenu；
- Tooltip；
- Tabs；
- Sidebar；
- Resizable；
- ScrollArea；
- Command；
- Badge；
- Table；
- Skeleton；
- Sheet；
- Collapsible。

该层保持通用，不包含 Node、Task、Run 等业务含义。

## 4.3 应用级组合组件

目录：

```text
components/app/
```

典型组件：

- AppShell；
- AppSidebar；
- WorkspaceHeader；
- InspectorPanel；
- CommandPalette；
- EmptyState；
- LoadingBoundary；
- ErrorState；
- SplitWorkspace；
- PageToolbar。

## 4.4 领域组件

目录建议：

```text
components/domain/
├─ project/
├─ baseline/
├─ node/
├─ edge/
├─ task/
├─ context/
├─ run/
├─ artifact/
└─ approval/
```

首批领域组件：

```text
NodeTypeBadge
NodeVersionSelector
NodeRelationList
EdgeTypeLabel
BaselineStatusBadge
BaselineSummary
TaskStatusBadge
TaskAcceptanceList
RunStatusBadge
RunOutcomeBadge
RunTimelineEvent
ContextItemCard
ContextAuthorityBadge
ContextTokenBudget
ContextConflictPanel
SnapshotFreshnessBadge
ArtifactTypeBadge
ArtifactDiffViewer
ApprovalRiskPanel
```

所有页面优先组合领域组件，避免重复写状态映射和样式逻辑。

## 4.5 页面与流程

页面只负责：

- 数据获取；
- 路由；
- 布局；
- 组合领域组件；
- 触发应用命令。

不得在单个页面中长期堆积大量临时组件和状态色判断。

# 五、默认应用骨架

Canvas Agent 采用桌面优先的三栏工作台：

```text
┌──────────────┬────────────────────────────────┬──────────────────┐
│ 项目导航      │ 当前主工作区                    │ Inspector        │
│              │                                │                  │
│ Dashboard    │ Node / Task / Context / Run    │ Details          │
│ Outline      │ Artifact / Baseline / Canvas   │ Relations        │
│ Tasks        │                                │ Context          │
│ Runs         │                                │ History          │
│ Artifacts    │                                │                  │
└──────────────┴────────────────────────────────┴──────────────────┘
```

## 5.1 左侧导航

使用 `Sidebar`，承担：

- 项目切换；
- Dashboard；
- Outline；
- Tasks；
- Runs；
- Artifacts；
- Baselines；
- Settings。

侧栏支持折叠为图标模式。

## 5.2 中央工作区

根据当前路由显示：

- Node Workspace；
- Task Workspace；
- Context Composer；
- Run Timeline；
- Artifact Review；
- Baseline Review；
- 局部 Canvas。

## 5.3 右侧 Inspector

使用 `Resizable` 与 `Tabs`，展示：

- Details；
- Relations；
- Context；
- History；
- References。

右栏可收起，不应阻塞中央任务。

## 5.4 全局交互

- `Command`：快速导航、创建对象、执行动作；
- `Dialog / AlertDialog`：创建、确认和高风险操作；
- `Sheet`：窄屏或临时辅助面板；
- `ContextMenu`：大纲与关系对象的快捷操作；
- 底部状态区：显示正在执行的 Run、后台任务和连接状态。

# 六、核心页面设计基调

## 6.1 Project Dashboard

回答：

> 当前发生了什么，我下一步应该处理什么？

优先显示：

- Active Task；
- Failed / Interrupted Run；
- Pending Approval；
- Stale / Diverged Snapshot；
- 最近 Artifact；
- 当前 Active Baseline；
- 下一步建议。

不以大面积统计卡片和图表为主。

## 6.2 Project Outline

采用类似 IDE 文件树的结构，支持：

- 分组与折叠；
- Node 类型图标；
- 行内重命名；
- 右键菜单；
- 拖动仅用于排序或显式父子关系调整；
- 搜索与过滤；
- 当前对象定位。

视觉位置不自动生成业务语义。

## 6.3 Node Workspace

中央区域展示 Node 当前版本内容。

右侧展示：

- 当前版本；
- 历史版本；
- Edge 关系；
- 所属 Baseline；
- 相关 Task；
- 影响对象。

Canvas 只作为“查看关系”和“影响分析”的入口。

## 6.4 Task Workspace

主要区域：

- Objective；
- Description；
- Non-goals；
- Acceptance Criteria；
- Targets；
- Dependencies；
- Current Snapshot；
- Runs。

状态、验收和执行结果必须清晰分离。

## 6.5 Context Composer

这是 MVP 的标志性界面，采用三列结构：

```text
候选上下文
    │
已选择上下文
    │
分析、冲突与 Token 预算
```

至少展示：

- 来源类型；
- 选择原因；
- 权威级别；
- 版本；
- Repository Revision；
- 优先级；
- Token 估算；
- 是否用户固定；
- 冲突与缺失项。

不能退化为普通多选表单。

## 6.6 Run Timeline

采用时间线，而不是 Canvas。

事件分层：

- Run 状态；
- Agent 消息；
- Tool Invocation；
- Test Result；
- Checkpoint；
- Artifact；
- Approval。

高频、低价值事件默认折叠；关键失败、等待输入和风险操作突出展示。

## 6.7 Artifact Review

重点支持：

- Patch / Diff；
- 测试报告；
- 生成文档；
- 数据库迁移；
- 执行总结。

评审动作必须明确区分：

```text
接受产物
拒绝产物
要求返工
应用 Patch
生成 Baseline Draft
```

## 6.8 局部 Canvas

只用于：

- 一跳或按需展开关系；
- 上下游依赖；
- 影响分析；
- Context 来源展示；
- 需求—设计—组件追踪。

默认不加载整个项目，也不承载执行日志和长文档。

# 七、密度、响应式与主题

## 7.1 密度

默认使用 Rhea 的紧凑密度。

原则：

- 主列表行高偏紧凑；
- 表单编辑区适度放宽；
- 关键确认与风险提示保留充足空间；
- 不通过缩小字体制造信息密度；
- 同类页面使用统一控件高度。

Mira 仅用于早期 A/B 静态原型，验证更高密度是否影响理解。

## 7.2 响应式策略

产品为桌面优先，不强求手机端完整功能。

建议：

- 推荐宽度：1440px 及以上；
- 最低完整工作区宽度：约 1180px；
- 中等宽度时收起 Inspector；
- 更窄时 Sidebar 折叠，并使用 Sheet 展示辅助信息；
- 手机端只提供状态查看、Approval 和简单回复，不承担完整 Context Composer 或 Canvas 编辑。

## 7.3 深浅主题

浅色和深色主题必须从 UI Foundation 阶段同时验证。

状态色不得只依赖颜色表达，还应结合：

- 图标；
- 文案；
- 形状；
- 边框或背景差异。

# 八、组件开发规则

## 8.1 基础组件修改规则

`components/ui/` 可以修改，但应保持稳定。

只有以下情况直接修改基础组件：

- 全局 Token 变化；
- 通用可访问性问题；
- 所有页面都需要的统一行为；
- 已确认的设计系统升级。

单个业务场景的特殊需求应在领域组件中组合实现。

## 8.2 禁止混用多个视觉体系

第三方库接入时必须通过适配层统一：

- 字体；
- 颜色；
- 圆角；
- 控件高度；
- Focus Ring；
- Empty / Loading / Error 状态。

不得在同一产品中同时保留 Ant Design、MUI、Mantine 等明显不同的默认视觉语言。

## 8.3 图标规则

- 默认统一使用 Lucide；
- 同一语义只使用一个固定图标；
- 普通操作默认 16px；
- 空状态和引导场景可以使用更大尺寸；
- 图标不能替代关键操作文字；
- 禁止混用多套线性图标。

## 8.4 表格规则

复杂表格使用 TanStack Table 提供逻辑，展示层使用项目组件。

表格应支持：

- 列显隐；
- 排序；
- 筛选；
- 行选择；
- 空状态；
- 加载状态；
- 键盘焦点；
- 必要时虚拟化。

不要为了使用表格而把所有对象都做成表格。

## 8.5 Canvas 规则

React Flow 节点必须使用项目 Token 和领域组件。

节点外观不得另起一套设计语言。Canvas 工具栏、Popover、Context Menu、Inspector 继续复用 shadcn/ui。

---

# 九、AI 辅助开发规则

所有 AI 编程 Agent 应遵守：

1. 新页面优先复用现有 `components/ui`、`components/app` 和 `components/domain`；
2. 禁止绕过现有 Button、Badge、Dialog、Tabs 等组件重新创建相似实现；
3. 禁止在业务页面中随意硬编码颜色、阴影和圆角；
4. 新增状态展示前先检查是否已有领域 Badge；
5. 新增第三方 UI 依赖必须说明现有体系无法满足的能力；
6. 新领域组件必须包含明确 Props 类型和状态边界；
7. 页面必须覆盖 Loading、Empty、Error、Disabled、Read-only 状态；
8. 不自动套用营销型 Dashboard Blocks；
9. 不为了视觉效果改变已经确认的信息架构；
10. 修改基础组件时必须说明影响范围。

后续可建立 Canvas Agent 自定义 shadcn Registry，用于分发：

- 领域组件；
- 页面骨架；
- Token；
- 项目约定；
- Agent 开发规则。

---

# 十、无障碍与键盘交互

MVP 必须具备：

- 可见 Focus Ring；
- 合理的 Tab 顺序；
- Dialog 焦点锁定与恢复；
- Tooltip 不能承载唯一关键信息；
- 图标按钮包含可访问名称；
- 状态不只通过颜色表达；
- Resizable 面板支持键盘操作；
- Command Palette 支持搜索和快捷键；
- 树、大纲、表格和菜单具备基本键盘导航。

建议首批快捷键：

```text
⌘/Ctrl + K：Command Palette
⌘/Ctrl + P：快速打开对象
⌘/Ctrl + Enter：执行当前主要动作
⌘/Ctrl + S：保存 Draft
Esc：关闭浮层或退出当前临时模式
```

快捷键必须可发现、可配置，并避免覆盖编辑器固有快捷键。

3. Node Workspace；
4. Task Workspace；
5. Context Composer；

# 十二、验收标准

UI Foundation 达到以下条件后，才能进入完整业务开发：

1. 浅色与深色主题均可正常使用；
2. 相同状态在所有页面中具有一致视觉表达；
3. 页面没有明显混用其他组件库默认风格；
4. 用户能够从 Dashboard 进入 Task，再进入 Context Composer；
5. Context Composer 能清晰区分候选、已选、强制项、冲突和 Token 预算；
6. Run Timeline 能区分状态、工具、测试、Artifact 和 Approval；
7. 主流程可以仅用键盘完成基本导航；
8. 1440px 和约 1180px 宽度下布局均可工作；
9. 领域组件没有散落重复的状态映射；
10. Agent 新增页面时能够复用现有组件而不产生明显视觉漂移。

# 十三、暂缓决定

以下内容等 UI 原型后再确认：

- 最终品牌主色；
- 最终字体组合；
- Rhea 是否需要局部进一步压缩；
- Canvas 节点的最终视觉形态；
- Run Timeline 的事件密度；
- Inspector 默认宽度；
- 是否加入全局底部状态栏；
- 动画库及页面级过渡；
- 移动端支持范围；
- 是否发布公开 Canvas Agent Registry。

这些问题不会影响当前 UI Foundation 开发。

---

# 十四、固定结论

1. shadcn/ui 是 Canvas Agent 的基础设计系统；
2. Base UI 是新项目默认组件底层；
3. Rhea 是默认视觉风格；
4. Tailwind CSS 与 CSS Variables 承担主题和 Token；
5. Lucide 是唯一默认图标体系；
6. TanStack Table 只提供复杂表格逻辑，不引入独立视觉语言；
7. React Flow 仅用于局部关系场景；
8. Canvas Agent 必须建立自己的领域组件层；
9. 产品采用桌面优先、高密度、多面板工作台；
10. UI Foundation 必须先使用 MUSICDB 数据验证，再连接完整后端；
11. 不直接把 shadcn Blocks 当作产品信息架构；
12. 不允许 AI 或开发者绕开设计系统随意创建重复基础组件。

# 十五、官方资料依据

- shadcn/ui Introduction：Open Code、Beautiful Defaults、AI-Ready；
- shadcn/ui `create`：可选择组件底层、视觉风格、图标、颜色和字体；
- shadcn/ui Rhea：面向空间敏感产品界面的紧凑风格；
- shadcn/ui Base UI 更新：新项目默认使用 Base UI，Radix 继续受支持；

- Base UI：无样式、可访问、可组合的 React 组件基础；
- TanStack Table：Headless 表格逻辑，可与自定义设计系统结合；
- React Flow：支持自定义 React 节点，并提供基于 shadcn/ui 与 Tailwind 的 React Flow UI。
