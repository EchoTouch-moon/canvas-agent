# 材料合并与冲突处理说明

## 1. 来源材料

本次整理使用：

- Canvas Agent 项目总体总结；
- Canvas Agent 项目规划阶段总结（v0.1）；
- Canvas Agent 核心领域模型决策基线（v0.2）；
- Canvas Agent 核心业务闭环设计基线（v0.3）；
- Canvas Agent 产品形态与多视图交互架构规划；
- 面向 Canvas Agent 的无状态执行与显式状态基础设施设计报告；
- 上传材料之后，在当前对话中确认的 ExecutionRequest 设计和“停止继续穷举设计、进入原型开发”的决定。

## 2. 决策优先级

冲突时按以下顺序处理：

1. 当前对话中用户明确“确认”的最新决定；
2. Planning Baseline v0.3；
3. Domain Planning Baseline v0.2；
4. Planning Baseline v0.1；
5. 产品形态与多视图规划；
6. 项目总体总结与基础设施报告中的早期建议。

## 3. 已处理的主要冲突

### 3.1 Graph 容器

早期材料存在 `Project → Graph → Node / Edge`。最终决定：不设置强制 Graph 容器，Node、Edge 直接属于 Project。

### 3.2 Canvas 是控制平面还是视图

早期报告曾使用“Canvas / Control Plane”。最终产品层面改为“项目控制系统”，Canvas 仅为关系地图和高级视图。控制平面是整个应用，不等同于 Canvas 页面。

### 3.3 哪些对象是 Node

早期资料曾将页面、接口、代码文件、测试、任务和 Artifact 广泛放入图中。最终 MVP Node 类型固定为 IDEA、GOAL、REQUIREMENT、CONSTRAINT、DESIGN、DECISION、COMPONENT；其他对象使用独立实体或 Git。

### 3.4 ContextSnapshot 的范围

早期资料可能将 Agent 运行中读取的所有信息视为 Snapshot 内容。最终定义：Snapshot 只冻结初始上下文；动态工具读取通过 RunEvent / ToolInvocation 记录。

### 3.5 Task 与验收

后续设计增加 TaskDraft、TaskSpecVersion、TaskTarget、AcceptanceCriterion 和 AcceptanceEvaluation，替代早期只有 Task / Run 的简单关系。

### 3.6 Run 状态

最终采用 status + outcome 双维度，避免把基础设施完成与任务结果满足混为一谈。

### 3.7 Checkpoint 与 Artifact

早期报告中的字段和生命周期仅作为候选参考。当前主基线明确将其详细协议延期到真实 Worker 原型之后。

### 3.8 技术基础设施

PostgreSQL、Redis、Object Storage、Task Queue 和 Vector Index 均是早期建议，不是已确认技术选型。MVP 的具体桌面形态和存储方案仍待技术 ADR。

## 4. 内容去重原则

- 产品定位只在主文档和产品专题完整表达；
- 领域实体规则集中在领域模型专题；
- 视图和交互集中在产品形态专题；
- 早期背景分析不重复进入每份文档；
- 相同原则在主文档保留简版，在专题文档保留可实施细节。

## 5. 文档维护建议

后续每次确认重大决定时：

1. 先增加或更新 ADR；
2. 更新对应专题文档；
3. 仅在影响项目总貌时更新主基线；
4. 旧决定标记 Superseded，不删除历史原因；
5. 延期内容在进入开发时从 DEFERRED 变为 PROPOSED，再经评审变为 CONFIRMED。
