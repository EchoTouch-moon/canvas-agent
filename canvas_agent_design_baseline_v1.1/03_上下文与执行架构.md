# Canvas Agent 上下文与执行架构

## 1. ContextSnapshot

### 1.1 定义

ContextSnapshot 是某个 TaskSpecVersion 在某个 Baseline 和 RepositoryRevision 上的不可变初始上下文包。

```text
Agent 实际看到的全部信息
= ContextSnapshot
+ Run 中后续 ToolInvocation / RunEvent 产生的信息
```

因此运行中读取更多代码不会修改旧 Snapshot。

### 1.2 顶层绑定

```text
project_id
task_id
task_spec_version_id
base_baseline_id
expected_repository_revision_id
```

Run 记录 actual_repository_revision_id，并在启动时校验一致性。

### 1.3 RepositoryRevision

本地优先环境不能只记录 Commit，应表达：

```text
base_commit
working_tree_patch_hash
tree_hash
```

### 1.4 Item 类型

```text
NODE_VERSION
EDGE
REPOSITORY_CONTENT
ARTIFACT
USER_INPUT
PROJECT_RULE
```

TaskSpecVersion 和 AcceptanceCriterion 属于顶层强制内容。

### 1.5 内容冻结

每个 Item 保存：

```text
来源引用
解析后的具体内容
内容 Hash
选择来源与理由
权威等级
优先级
Token 估算
```

内容通过 ContentBlob 按 Hash 去重。

### 1.6 权威等级

```text
PROJECT_RULE
> TASK_INSTRUCTION
> PROJECT_FACT
> EVIDENCE
> REFERENCE
> UNTRUSTED_CONTENT
```

代码、日志或外部文本中的指令不得覆盖任务和项目规则。

### 1.7 Token 预算

```text
P0：强制保留
P1：直接相关
P2：辅助相关
P3：背景参考
```

P0 超限时必须缩小任务、切换模型或人工压缩，不允许静默截断。

### 1.8 代码表示

```text
FULL_FILE
SYMBOL
LINE_RANGE
DIFF
SUMMARY
METADATA
```

即将修改的关键代码不能只提供 SUMMARY。

### 1.9 冻结与派生

Snapshot 状态：DRAFT、FROZEN、ARCHIVED；适用性：CURRENT、STALE、DIVERGED、ARCHIVED。

冻结后不得增删 Item、改变顺序、切换 Baseline 或代码版本。任何调整创建派生 Snapshot。

## 2. Context Composer

### 2.1 流程

```text
选择 TaskSpecVersion
→ 确定 Base Baseline
→ 冻结 Expected RepositoryRevision
→ 加入强制内容
→ 根据 Edge 与文件映射推荐候选
→ 用户加入、排除、固定
→ 冲突检查
→ Token 预算处理
→ 保存内容和 Hash
→ FROZEN
```

### 2.2 冲突检查

- 同一 Node 多版本未标记比较用途；
- Edge 锚定版本与选择内容不一致；
- Primary Base 代码混用多个 Revision；
- ProjectRule 与 UserInput 冲突；
- TaskTarget 与 Snapshot 版本不一致；
- 重复内容；
- 关键内容超出 Token 预算。

### 2.3 推荐策略

MVP 先使用：

- TaskTarget；
- Edge 一跳关系；
- Component 与仓库路径映射；
- 当前 Baseline；
- 最近相关失败报告。

不要求第一版对整个仓库建立向量索引。

## 3. ExecutionRequest

### 3.1 定义

调度系统交给 Worker 的不可变、自包含或可准确解析的执行合同。

### 3.2 主要内容

```text
execution_request_id
run_id
worker_attempt_number
task_spec_version_id
context_snapshot_id
expected_repository_revision_id
checkpoint_id (nullable)
worker_profile_requirement
agent_configuration
tool_policy
workspace_strategy
resource_budget
schema_version
request_hash
expires_at
```

### 3.3 一个 Run 多个请求

Approval、用户输入、中断恢复或 Worker 更换后，可以为同一个 Run 创建新的 ExecutionRequest。不同片段用 worker_attempt_number 区分。

### 3.4 Worker Capability 与 ToolPolicy

```text
Worker Capability：环境具备哪些能力
ToolPolicy：本次执行被允许使用哪些能力
```

调度前必须满足：

```text
required_capabilities ⊆ worker.capabilities
```

### 3.5 工作区

MVP 默认：

```text
ISOLATED_WORKTREE
```

执行流程：

```text
用户仓库
→ 创建隔离工作区
→ Worker 修改和测试
→ 生成 Diff / Patch
→ 用户审查
→ 应用到用户仓库
```

### 3.6 资源预算

请求应限制运行时间、工具次数、模型迭代、Token、成本和磁盘使用。达到阈值时应保存当前结果和 Checkpoint，而不是无记录退出。

## 4. Worker

Worker 只负责：

```text
读取 ExecutionRequest
→ 校验 Hash、Schema、Revision 和权限
→ 加载 Snapshot 与可选 Checkpoint
→ 在隔离工作区调用 Agent 和工具
→ 回传事件和结果
→ 释放或被替换
```

Worker 不应：

- 自行使用最新 Task 或 Baseline；
- 自行更换 Snapshot；
- 未经 ToolPolicy 调用能力；
- 把内存当作唯一恢复来源；
- 直接把 Agent 建议写入 Active Baseline。

## 5. 安全与可靠性

- 有副作用操作使用幂等键；
- 高风险操作进入 Approval；
- Approval 绑定参数 Hash 和代码版本；
- Worker 领取使用 compare-and-set；
- Snapshot、Request 和 Checkpoint 使用完整性 Hash；
- Git 是代码事实的权威来源；
- Redis 或队列只能保存短期调度状态，不是长期项目事实的唯一存储。

## 6. 开发时再确定的协议【DEFERRED】

- RunEvent 标准事件和顺序号；
- ToolInvocation 输入输出、错误与幂等协议；
- Checkpoint 内容和恢复粒度；
- Artifact 接受、应用、拒绝与回写；
- 具体 CLI Agent 适配；
- 完整队列、多 Worker 和分布式租约。

实现这些模块前，应先用真实 Worker 原型观察实际数据，再做最终模型。
