
## t2：失败不是单纯的 call limit

`c1-t2-multi-file-migration-v1` 的 16 个 run 中：

- 4 个 end-to-end success；
- 5 个 oracle 通过，但其中 1 个在 24-call 上限时仍被判为 `BUDGET_EXHAUSTED`；
- 10 个 `BUDGET_EXHAUSTED`；
- 1 个 `TERMINAL_FAILED`；
- 11 个 unrecovered tool failure run；
- 15/16 run 至少出现一个 tool error。

tool error 的类型分布为：

```text
read   = 5
edit   = 20
bash   = 28
```

4 个成功 run 都完成了 9 个预期 writable paths；它们有 7 个 tool errors，但全部是可恢复的 bash error。
12 个非成功 run 的 error events 为 46 个，其中 5 个 read、20 个 edit、21 个 bash，11 个 run 未恢复。

| t2 子集                 | calls 均值 / 中位数 | tool requests 均值 | tool errors 均值 | 首次 error 中位数 | duplicate hash run |
| ----------------------- | ------------------: | -----------------: | ---------------: | ----------------: | -----------------: |
| 4 个 end-to-end success |        18.75 / 19.5 |              31.25 |             1.75 |               9.5 |                2/4 |
| 12 个非成功 run         |          20.92 / 24 |              30.33 |             3.83 |                 7 |               8/12 |

非成功 run 的 tool-request 数并没有明显高于成功 run，但 error 数更高、首次 error 更早，且更常出现重复
argument hash；其中 3 个 run 出现连续重复 hash。重复 read 本身可能是合理复查，所以这些 hash 只能证明
重复请求，不直接等同于“无效循环”。不过结合 24-call exhaustion、edit/read error 和无法恢复的 tool error，
证据支持“工具错误后的恢复轨迹失稳”是主要候选原因，单纯把预算从 24 调高并不能解决已识别问题。

### 成功轨迹的共同点

4 个成功 t2 run 的共同结构是：在 13–23 calls 内完成 9 个 writable paths，tool error 只出现在 bash，
最终 objective/regression oracle 均通过。它们的 tool requests 中 read/edit/bash 都形成了明确的迁移链，
没有连续重复的 exact argument hash。

### 非成功轨迹的分叉

- 1 个 run 在 4 calls 时提前结束，未产生 edit，objective oracle 失败；
- 1 个 run 在 7 calls 时因 read error 后终止，未产生 edit；
- 10 个 budget-exhausted run 中，多个在早期 read/edit error 后进入继续尝试；部分只完成 2–8 个 writable paths，
  另有少数完成全部 9 个 paths 但没有在 call 24 前形成 terminal outcome；
- metadata 能看到 `models/product.js`、`services/pricing.js`、`services/billing.js` 等路径在 error 后再次 read/edit，
  但无法从已保存证据恢复失败 command 的具体内容。

## Token 与 call 轨迹

t2 成功 run 的总 token 中位数为 191,668，非成功 run 为 216,381；tool request 均值反而接近（31.25 对 30.33）。
这说明非成功结果更像是高 token 消耗下的恢复/终止失稳，而不是简单“调用更多工具”造成的。该描述是
diagnostic association，不是因果估计。

t1 的 16 个 run 在 9–15 calls 内全部终止；t2 的 successful run 在 13–23 calls 终止，非成功 run 的中位数为
24 calls。F0 的 `24` budget 因而确实切到了 t2 的 failure boundary，但现有轨迹同时显示 edit/read/bash error
和重复请求，不能把下一步简化为扩容预算。

## 当前可判定与不可判定

### 可以判定

1. t1 的核心诊断和 oracle 通路已经稳定，剩余问题是 collateral write / writable-scope fidelity。
2. t2 的主要失败模式是多文件迁移中的 tool error recovery、重复请求和终止前未完成，而不是单一 oracle 缺陷。
3. t2 的 successful subset 与 non-success subset 在 calls、tool requests、error 类型和首次 error 位置上存在可见分叉。
4. F0 `VALIDITY/PRECISION PASS + FEASIBILITY FAIL` 的裁决由真实 Native 轨迹支持，不是 evidence 丢失造成的假阴性。

### 仍不可判定

- 两个 t1 run 修改 `package-lock.json` 的具体 bash command 或工具副作用来源；
- 每个 bash/read/edit error 的原始 provider 参数与返回文本；
- t2 某次错误的根因究竟来自 benchmark/task design、tool envelope、prompt、model capability 还是它们的组合；
- 增加预算后是否会改善 t2，或只是延长恢复循环。

## 下一步边界

F0-RCA 不改变原 F0 contract，也不启动 T0/E1。下一阶段如果要修复：

1. 先为未来执行增加不泄漏原文的副作用 provenance（safe command class/hash、exit class、changed-path source），
   让 scope violation 可以归因；
2. 针对 t2 的 read/edit/bash error recovery 设计小范围工程修复或 task/prompt 修订；
3. 任一 prompt、tool envelope、fixture、scope 或 budget 改动都建立新的 F0 contract、execution revision 和 study identity；
4. 新 F0-v2 通过独立 review 和授权前，不执行 T0；T0 与 E1 继续 `HOLD`。
